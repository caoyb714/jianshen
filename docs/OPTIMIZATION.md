# HerFit 优化计划（v0.8 提案）

> 定稿日期：2026-11-18。状态：**方案已定，尚未实施**。
> 输入：外部对标（Keep / openGym / wger / workout-cool / SparkyFitness）、视觉规范 v4、体验规范（含增补）、工程落地评估。
> 纪律：本文只描述要做什么与为什么，不代表已完成。代码改动一律另起提交，并同步测试基线。

## 0. 结论先行

三个问题的根因都不是"功能没做"，而是**位置放错了**：

1. **AI 说明不是模型不行，是它没有后果。** 现在它被约束成"只能解释、不能改变任何数字"，输出一段 60–120 字的散文，而同一屏下方还有一块由规则引擎算出、可确认生成新版本的「负荷调整建议」。前者读起来自然像废话。正确的位置是：**可执行部分交回规则引擎，AI 只写每条建议的理由**。
2. **体重不是没有记录能力，是入口藏起来了。** 体重只存在于每日指标里，且默认被「显示体重记录」开关隐藏，档案页自然看不到。补法不是再加一个字段，而是**把已有的单一数据源暴露出来**：记录页可写、我的页只读、成长页随开关联动。
3. **界面问题集中在三处工程细节**：字号阶梯碎了（9.5/10/10.5/11/11.5 五档低于 12px 并存）、灰阶有噪声没层级（五个近似灰各硬编码十几处）、危险色缺失（确认删除与品牌色亮度接近，读不出等级）。

### 2.2 体重缺口

数据其实一直在：`metricSchema.weight`（20–400，可空）。问题在三处：只在记录页可写、被 `settings.showWeight` 整体隐藏、档案页完全看不到。**不需要新增字段**。

### 2.3 视觉三条

1. 字号阶梯碎片化，低于 12px 的五档并存（`.set-cell label` 9.5px、移动端 `.status-chip` 9px）。
2. 灰阶近似值各写各的（`#78636f` 出现 12 次，另有四个近似值），全站只有 6 个变量，层级读不出来。
3. 面板与页面底色对比仅约 1.1:1，全站只有 Modal 有阴影；破坏性操作沿用品牌色，危险等级无法识别。

## 3. 方案

### 3.1 体重：单源 + 只读镜像

**不新增 `profile.weight`。** 体重只存 `metrics[].weight`，避免两个数据源必然打架。

| 位置    | 行为                                                                   |
| ------- | ---------------------------------------------------------------------- |
| 记录页  | 独立体重块（唯一写入口）。只写今天，同天再存＝覆盖；清空输入＝保留原值 |
| 我的页  | 只读镜像，同一数据；提供「记录体重」跳转                               |
| 成长页  | 已有 `showWeight` 分支，只需补 tab 与列的回退一致性                    |
| AI 请求 | **不含体重**，写成不变量并由单测守住                                   |

**派生规则**：当前值＝按日期倒序最近一条**非空且 ≥20** 的 weight；变化＝与上一条非空的差；「今天已记录」独立判断，不决定主值。`0` 与 `null` 一律视为无效，防止把曲线拉平。

**视觉规格**：独立 `.panel`，标题 h2「体重」（与「今天喝水了吗？」同构，不加图标）；主值 28px/600 + 13px 单位；变化行 12px 中性表述「较上次 +0.4 kg · 最近一次 12/03」，不用箭头、不用红绿；动作行「记录体重」/「更新今天的体重」；末行免责「体重只是参考，不设目标，也不计入任何评分。」

**三态**：从未记录且开关开着 → 整块不渲染；开关关闭 → 保留标题「体重」+ 一句「体重记录已隐藏」+「在设置里打开」，**壳内不得出现任何数字或日期**；有记录 → 四层全显。关闭态高度约 120px，不撑满开启态 242px。

### 3.2 AI 与规则建议合并为一块「今天可以这样调」

**分工**：幅度标签只能来自 `suggest()` / `adjustLabel()`；AI 只写每条 ≤40 字的「依据」，且必须复述本地实测数字（次数、负荷、难度）。对不上就丢弃该条文本，不降级成自由发挥。

**接口形状**（`/api/explain` 改造）：

```
请求 { planVersion, day:{focus, slots[]}, items:[{ sig, label, evidence:{reps,load,difficulty} }] }
响应 { ok:true, items:[{ sig, text }] }
```

服务端以请求里的 `sig` 建白名单：未知 sig 丢弃、`text` 超 40 字截断、文本中数字必须属于该条 `evidence`、最多 6 条、单条下限 8 字。整体坏 JSON 返回 `{ok:true, items:[]}`（降级而非报错）。4KB 预检、5 次/分限流、12 秒中止、控制字符清洗保持不变。

**采纳语义：草稿 → 生成新版本**（与「计划不可变」一致）

1. 点「采纳」只进本地草稿（组件 state，不落库、不写 localStorage），周计划文本不变。
2. 卡底「按 N 条生成新版本」才 `applyAdjustments` + `commit(plan)`：版本 +1、旧版归档。
3. 提交前比对 `plan.id + version` stamp，不一致硬拒，草稿转「计划已更新，需在新版本上重建」，给「在新版本上重试」或「放弃」。
4. 条目状态机按「计划有没有变」分四态，**草稿期没有版本号，不得写 v14**：

   | 态                | 触发                          | 状态行                             | 操作                                                                                                    |
   | ----------------- | ----------------------------- | ---------------------------------- | ------------------------------------------------------------------------------------------------------- |
   | S0 未采纳         | 初始                          | 依据为普通行                       | 采纳 / 忽略                                                                                             |
   | S1 已采纳（草稿） | 点采纳                        | 「已采纳 · 下次生成计划时应用」    | 「移出本次调整」（移出草稿，不提交、不产生版本、不弹窗，回 S0，`aria-label`「移出本次调整，计划不变」） |
   | S2 已提交         | 卡底「按 N 条建议生成新版本」 | 「已生效 · v14，撤销不会改回旧版」 | 「撤销并生成新版本」（提交 v15 → S3）                                                                   |
   | S3 已撤销         | 撤销成功                      | 「已撤销 · v15」                   | 「采纳」（**与 S0 同名同效**：进草稿、回 S1、卡底计数 +1，不单独提交）                                  |

   **词表只有五个**：采纳 / 忽略 / 移出本次调整 / 撤销并生成新版本 / 恢复。「恢复」只用于已忽略项（回未采纳列表，不进草稿），与「采纳」后果不同，不合并。「再采纳」这类只为区分"从哪来"、后果却相同的词一律不用。pending 只出现在两处：卡底「正在生成 v14…」与 S2 的「正在生成 v15…」，S3 条目没有 pending。

   **四态视觉**：绿色只给 S2——「已采纳」与「已生效」不是程度差别而是性质差别（计划变没变），S1 若也用绿色，用户会以为已经进计划。S1 用浅灰粉左边线 `#d8bec8` + 底 `#fffdfc`，S2 用 `#9baf95` + `#f7faf3`；S1 与 S2 同高同构（约 131px），只分叉配色与文案，状态切换时结构不跳。S2 的按钮文案用「撤销并生成新版本」，避免与 S1 的即时撤销同形不同义。

   **卡底提交通道**：「按 N 条建议生成新版本」是整卡唯一 commit 入口，用 `.button.secondary`，不用 primary——同页已有「开始今天的训练」占主按钮，两个玫瑰实心会争主次。顺序固定为：条目 → 已忽略折叠 → 提交按钮 → 卡底署名；草稿 0 条时不渲染。**S3 的「再采纳」不得绕过这个入口**：它等同首次采纳，只把条目放回草稿并让计数 +1，提交统一由卡底完成。同一个按钮在两种状态下产生两种后果（一次进草稿、一次直接提交）会让用户无法预测，这条优先于「少点一次」的便利。

   **依据的位置**：S0/S3 为普通行（缺省不留空行）；S1/S2 折叠在状态行右侧（summary 36px），展开就地一行 12px，无边框、不缩进。触发器**挂在状态行而不是操作行**——这是 pending 期间仍能回看依据的原因，实现时不要挪位。卡底提交按钮不 sticky：同页 `.rest-timer` 已经是 sticky，再叠一条粘附带滚动时会互相顶。

   **版本号必须插值**：所有文案里的版本号一律取 `plan.version`，禁止写死。失败态若固定成「仍是 v13」，到 v15/v16 时每次失败都会说谎，属事实性错误而非风格问题。

5. **撤销不做反向数学**（+1 kg 反算 −1 kg 会累积误差）：取该版本之前的基线计划 days，套用**剩余采纳项**重跑 `applyAdjustments`（纯函数、幂等）后提交。这样「改 3 条撤回 1 条」也自然得到正解，不必记录每组历史值。

6. **pending 期间不用原生 `disabled`**：改用 `aria-disabled="true"` + 处理函数首行 return，另加 in-flight 布尔锁。原生 `disabled` 会把键盘焦点弹回页面根部，恰好在「正在生成…」这一刻丢焦点。控件复用同一 DOM 节点，只换文案。

**触发与成本**：本地条目进页面即算，秒出、不需网络；AI 依据仅在「已同意 + 在线 + 有可执行建议 + 该版本当天未拉过」时延迟 800ms 拉一次；每版本每天自动 1 次、手动 ≤4 次，第 5 次进入 30 秒倒计时。失败、超时、离线只降级依据位，**不影响采纳**（采纳只依赖本地幅度）。

**署名**：卡底一行 12px「幅度由本地规则按你的记录计算；依据说明由 AI 改写，仅供参考」。AI 关闭或失败时换成「幅度由本地规则按你的记录计算」，不加色、不加粗、不换位置。

### 3.3 视觉收口

- **token 化**（值不变，只提取）：`--surface #fffcfa`、`--surface-2 #fffdfc`、`--ink #494047`、`--ink-3 #8a7580`、`--ok-bg #eaf0e4`、`--ok-ink #576b4c`、`--ok-line #cfdcc4`、`--warn-bg #f8e8de`、`--warn-ink #925d42`、`--danger #9b4454`、`--focus #9f6379`、`--shadow-1`。
- **新增刻度**：`--radius-sm 8 / -md 11 / -lg 20`；`--space-1…6 = 4/8/12/16/20/28`；字号 `--fs-note 12 / --fs-body 13 / --fs-sub 15 / --fs-title 18 / --fs-metric 28`，把 9.5/10.5/11/11.5 四档归并到 10（仅时间戳与单位）与 12（所有说明文字）。
- **色彩语义**：绿只表示完成/已采纳，土黄只表示中断/受阻，玫瑰只给品牌动作，**绝不用于删除**。
- **删除动线**：保持行内二次确认，一行只允许一个高权重要素——确认删除为小实心 `--danger`，取消降为 muted 文本按钮；`flex-wrap: nowrap` + `gap: 8px`，≤370px 才回退换行。
- **新增覆盖（现存缺陷）**：全局 `button:disabled { opacity: .48 }` 会把 12px 文字按钮糊成粉雾。补 `[aria-disabled='true'] { opacity: 1; color: var(--ink-3); cursor: default }`。

**三个技术难点**

1. **条目化接口**：服务端只按 `sig` 白名单回填，逐条校验数字子集；整体坏 JSON 降级为空数组而不是 500。
2. **草稿落点**：放组件 state，不入 localStorage；`{stamp, ids}` 随 `planStamp`/日期变化清空，杜绝孤儿数据；`applyAdjustments` 只接受 `Adjustment[]`，需从 `AugmentedAdjustment` 裁剪字段。
3. **版本 stamp**：演示模式取 `active.plan.id + version`；云模式取 `snapshot.plans` 的 active 行。`revisionFor` 对 plan 恒为 null，云端**没有乐观锁**，stamp 只能防误触——这是已知缺口，见第 7 节。

**风险（按严重度）**

| 级别 | 风险                                                                                                 | 规避                                                                                |
| ---- | ---------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |

## 6. 验收清单

**单测**：`latestWeight`（null / 0 / 20 / 乱序）、`mergeMetric` 保另一半、payload 递归无 weight 且 items ≤6、幅度标签只出自 `adjustLabel`、explain 白名单/数字不符丢弃/截断/坏 JSON 降级、stamp 比对。

**E2E（在既有 12 条上追加）**：

1. 档案表单与我的页任何位置都无体重输入
2. 同天二次保存覆盖同一行 metric，不产生重复行
3. 关开关后记录页输入、成长页 tab/列/曲线体重全消失，数据仍在，壳内无数字
4. 采纳 3 条未生成版本：`plans` 长度与 `active.plan.version` 均不变
5. 生成新版本后旧版 `archived`、版本 +1、条目转「已生效」

7. 草稿非空离开有行内确认；放弃后 `plans` 无新增
8. stamp 不一致时提交被拒并可「在新版本上重试」
9. AI 失败/离线时幅度标签与采纳仍可用，仅依据位缺省
10. 第 5 次手动重试进入 30 秒倒计时

12. 抓包断言：AI 请求体不含 weight 字段

## 7. 需要产品确认的三个决定

1. **是否给云端计划加版本互斥**：现在 `herfit_write` 的 plan 分支 `p_expected` 恒为 null，两台设备同时提交会互相覆盖。建议在 C 段之后单独做一次迁移（`herfit_write` 支持 plan 的 `p_expected`），属于数据安全项而非体验项。
2. **AI 与本地建议合并后的署名**：方案是"幅度由规则算、依据由 AI 写"。若你希望彻底去掉 AI（只留规则建议），B 段可缩减约 1 个半天，功能不残缺。
3. **体重的隐私默认值**：`showWeight` 现在默认关闭。体重块上线后，是否改为"首次记录时询问一次是否在概览中显示"，而不是继续默认隐藏。

## 8. 明确不做

- 不新增 `profile.weight`，不做两处体重数据源的同步。
- 不引入体脂率、围度目标、体重目标线（与"不以减重为目标"的产品红线冲突）。
- 不做 AI 自由对话、不做 AI 直接改计划、不做推送与穿戴设备接入。
- 不重做整体视觉风格，不引入新的 UI 库。
- 不在动作文案里出现「已审核」「专业处方」。
